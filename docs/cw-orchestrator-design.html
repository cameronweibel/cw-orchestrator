cw, the workspace routing orchestrator

A thin wrapper above claude-ws. You type a task, it decides which workspace fits, spawns a Claude session in tmux with that profile loaded, and drops you into it. claude-ws stays untouched.

The big picture

One command travels down four stages. Each stage already exists except the top two.

personal, cweibelbusiness@gmail.com hebbian, info@hebbian.ch convolving

How the router decides

Two steps. Naming the workspace yourself is a plain string match on your machine. Everything else goes to the Claude Code CLI on your normal Claude login, which decides using a rules file you write in plain language. There is no API key and no external API anywhere in this setup. Click a step in the diagram to inspect it.

Explicit name

No file and no call behind this step. cw compares your first word against the profile names in ~/.claude/profiles/. Prefixes work as long as they are unambiguous.

$ cw personal "book the dentist"
$ cw heb "fix the EAI pricing page"
$ cw conv "log the Metellus touch"

routing.md, the rules file

Lives at ~/.claude/orchestrator/routing.md. Plain language, no syntax. The agent, which is claude -p on your Claude Max login and nothing external, reads the whole file plus the folder you launched from before deciding. Add common requests, keywords, client and school names, and tie breakers under each workspace heading. Changes apply on the next launch. The file also grows on its own: every routed spawn echoes the pick and pauses, and if you correct it, cw asks for the general case and writes it in here for you. This is the file as it exists today, shortened.

## convolving
The AI consultancy. Clients, proposals,
invoices to clients, the CRM, outreach,
pipeline, leads, Hermes agents. Client
names like Metellus, SWISS, Cognigy.

## hebbian

The picker and routing.log

Below 0.7 confidence cw asks instead of guessing, since a wrong pick means the wrong Google account. Every decision, including refusals, lands in ~/.claude/orchestrator/routing.log. Skim it to spot repeat offenders, then add a line about them to routing.md.

cw: not sure which workspace fits
    (best guess: hebbian, confidence 0.65)
1) convolving  2) hebbian  3) personal
Select workspace:

# routing.log
12:11  tier=agent    ws=personal  conf=0.99
       task=book a dentist appointment
12:11  tier=refused  ws=hebbian   conf=0.65
       task=prepare slides for the ETH class

Living with the sessions

One shared tmux session named ws holds every Claude window. Listing, attaching and killing are thin tmux calls, so there is no separate state file to drift.

# spawn, route, attach
$ cw "reply to the ZIS parent email"

# spawn detached, keep your shell
$ cw -d "draft the SFF invoice"

# skip routing, name the workspace
$ cw hebbian "fix the EAI pricing page"

# headless, prints the result
$ cw -p "summarise unread mail"

# manage
$ cw home
$ cw ui
$ cw ls
$ cw a 2
$ cw peek 2
$ cw send 2 "yes, go ahead"
$ cw kill 3

# the orchestrator chat
$ cw master
$ cw ls
  1  personal/draft-sff      busy    4m
  2  hebbian/eai-pricing     input   1m
  3  convolving/crm-touch    done    22m

# under the hood
tmux new-window -t ws \
  -n "hebbian/eai-pricing" \
  claude-ws hebbian -- "<task>"

The task rides along as the first prompt, so the session starts working before you attach. Outside tmux, cw attaches. Inside tmux it switches windows instead, since nested attach fails. No tmux installed means a new iTerm tab via osascript, same routing.

What gets created

PathRole
~/.claude/bin/cwthe orchestrator, one bash script around 180 lines
~/.claude/orchestrator/routing.mdplain language routing rules the agent reads, yours to grow
~/.claude/orchestrator/routing.logdecision log for tuning the rules
~/.claude/workspaces.jsongains a one line description per workspace, feeds the classifier

Nothing else changes. Discovery, secrets, CLAUDE.md layering and workspace.env keep living in claude-ws, and Hermes plus ws-sweep keep calling it directly.

How to use it

Everything below is real output from the live test runs. All of this is installed and working.

1. Start something

Type a task in any terminal. cw picks the workspace, spawns the session in tmux, and attaches you. You land in a normal Claude Code session already working on the task, with the right profile loaded (check the [PERS], [HEBB] or [CONV] tag in the statusline). Detach with ctrl+b d and it keeps working.

$ cw "reply to the ZIS parent email about the schedule"

# stay in your shell instead
$ cw -d "book a dentist appointment for me next week"
spawned 0  personal/book-a-dentist-appointm

# name the workspace yourself, routing skipped
$ cw heb "fix the EAI pricing page"

# the agent echoes its pick and pauses 8 seconds.
# Enter or waiting accepts, typing a workspace corrects it,
# and a correction teaches routing.md a new rule by itself

    or type the right workspace: hebbian

> haircuts during school visits are hebbian

2. See what's running

cw ui (or bare cw once sessions exist) opens an arrow key picker over the live list, with each session's actual screen previewed on the right. Enter jumps into the highlighted session and you take it over as a normal Claude Code terminal, ctrl+b d hops back out, ctrl-x kills a session, ctrl-r refreshes. cw ls prints the same list without the interface. Four states: busy means the model is working, input means it stopped on a question and needs you, idle means it is ready for a prompt, done means it finished.

$ cw ui

  1    hebbian     eai-pricing            busy   1m   │ Tuesday 9:00 or Thursday
  2    convolving  crm-touch-sweep        input  8m   │ 14:00. Which one?
  3    -           master                 idle   2m   │
  enter attach   ctrl-x kill   ctrl-r refresh        │ (preview of highlighted
>                                                    │  session's screen)

3. Look inside and talk to a session

peek shows a session's screen, send types into it and presses Enter. This is how you answer a question a background session is stuck on without attaching. Jump in fully with cw a 0, close with cw kill 0.

$ cw peek 0
> book a dentist appointment for me next week
Claude: I found two slots, Tuesday 9:00 or Thursday 14:00. Which one?

$ cw send 0 "Thursday 14:00"
sent to 0

4. The master chat

cw master opens the orchestrator session. It has no email or Drive access, just preapproved cw and tmux commands, and it starts by sweeping the list. Talk to it in plain language and it drives the sub chats. Proven in testing: "what's everyone doing", "tell session 0 to also check the Friday slots", "spawn a session to draft the SFF invoice", "clean up the done sessions". It peeks before and after every send to confirm the instruction landed, and never kills anything you did not ask it to.

$ cw master

Claude: Status, two sessions up.

  Session 0 (personal) is a test session. It replied READY, answered
  a PONG check, and is now idle waiting for instructions.
  Session 1 is this master session.

  Nothing is blocked or asking questions. Ready for tasks.

5. Utilities

When routing gets something wrong, add a plain sentence about it under the right workspace heading in routing.md and the agent uses it on the next launch.

# dry run, spawns nothing
$ cw route "log the touch for the Metellus call"
workspace=convolving tier=agent confidence=0.98

# headless, prints the answer and exits
$ cw -p "summarise my unread mail"

# every routing decision
$ tail ~/.claude/orchestrator/routing.log

# teach the router, in ~/.claude/orchestrator/routing.md
## personal
... appointments like the dentist or the doctor ...

Decisions baked in

  1. Wrapper, not a rewrite. cw shells out to claude-ws so both entry points keep working and Hermes is unaffected.
  2. tmux over background processes. Attach, scrollback and visible permission prompts come free. A detached session that hits a permission question just waits until you attach, and cw ls surfaces it.
  3. Ask on low confidence. Never default to a workspace when unsure. An account mixup costs more than the picker.
  4. One task per session. A cross workspace task spawns into the primary workspace. A --multi flag can come later.

cw home, the control room

PRD for a light utility on top of cw. Status: BUILT and tested, 21 Aug 2026 (M1 core plus the M2 keys). Run cw home to use it. Decisions locked with Cameron: side pane list, up and down arrow keys, always on from first use.

Today each cw session lives in its own tmux window and you hop between them with cw ui or cw a. That works for dipping in, but there is no place to sit. cw home is that place: one always running screen with the master chat and every sub chat in a permanent list on the left, and whichever chat you highlight filling the rest of the screen as a normal Claude Code terminal. You leave it open on a monitor or reattach to it whenever you want; nothing dies when the terminal window closes.

Goals

  • One command, cw home, opens or reattaches the control room
  • Always visible list: master plus every sub session with live state
  • Up and down arrows move the highlight, Enter swaps the chat in
  • The open chat is a real Claude Code terminal, typing just works
  • A chat waiting on you (input state) is visible at a glance
  • Survives closing the terminal window, reattach any time

Non goals

  • No new daemon and no autostart at login, first use starts it
  • No API calls, everything is tmux and the existing cw script
  • No replacement of cw ui, the popup picker stays for quick hops
  • No web UI, this is a terminal utility
  • No change to how sessions spawn, route, or store state

What it looks like

Two panes in one terminal window. The list pane owns the arrow keys when focused; inside the chat the arrows behave normally, so one hop key (and the mouse) moves focus between the two.

States reuse the four from cw ls. busy means the model is working, idle means ready, done means finished. input renders as the attention state: the row is highlighted so a sub chat stuck on a question pulls your eye even while you type in another chat.

How it works

The nested client pattern. Nothing new runs in the background; the outer layout lives on its own tmux socket and the right pane is a second client attached to the existing ws server.

Everything reuses what cw already has: the row builder (cw __rows), the state detector (window_state), fzf, and the spawn and kill paths. Always on falls out for free, both tmux servers keep running after you close the terminal, and cw home reattaches to the same layout.

Tradeoffs and edge cases

CaseBehavior
tmux prefix inside the chatthe chat is a nested client, so reaching the inner server by hand needs the prefix twice. Rarely needed, cw commands cover the common actions.
double status barswhile a home client is attached, the inner ws session's status bar is switched off so only the outer layout draws chrome.
no sessions yetthe list shows an empty state with the hint "type n to start a task, m to open the master".
terminal resizethe list pane keeps a fixed width around 26 columns, the chat pane absorbs the rest.
done rowsfinished sessions stay listed and dimmed until killed with x, same as cw ls today.
arrow keys in the chatuntouched. The list only owns the arrows while it has focus, which is why the hop key exists.

Milestones and success

  1. M1, the core. cw home builds the layout, list with live states, arrows plus Enter switching, hop key, mouse focus, auto refresh.
  2. M2, attention and actions. input rows highlighted, n to spawn a routed task, x to kill with the busy guard, m for master.
  3. M3, polish. Resize behavior, empty state, reattach smoke test, docs on this page move from PRD to usage.

Done means: open a terminal, run cw home, move the highlight with the arrows and press Enter, and the chat swaps in fast. A sub chat that stops on a question shows as needs you within a few seconds. Close the terminal, reopen, cw home puts you back exactly where you were.
